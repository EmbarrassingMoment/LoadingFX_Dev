## Project

LoadingFX is an Unreal Engine 5 plugin: a library of material-based loading spinners, a loading icon display that keeps animating during blocking loads, and a lightweight asset loader. This repository is the development and sample project (`LoadingFX_Dev`). It is published on GitHub (MIT), and the plugin is distributed **for free** on Fab.

- **Target engines:** UE 5.5 – 5.8 (one Fab package per version).
- **Authoring engine: UE 5.5.** Content (`.uasset` / `.umap`) must stay loadable in 5.5, so never open or save this checkout's content with a newer engine. Use 5.6 – 5.8 for compile checks of the plugin (RunUAT `BuildPlugin`), and 5.8 for the MCP workbench, a separate worktree whose content is never committed (see UE 5.8 workbench below).
- **Platform:** Win64 (tested) and Linux (compile-checked on 5.5 and 5.8 on 2026-11-01, not run). Both are in every module's `PlatformAllowList`; Fab requires an allow or deny list per module, so the list stays. Other platforms after 1.0.

## Build & Setup

1. Right-click `LoadingFX_Dev.uproject` → **Generate Visual Studio project files**
2. Open `LoadingFX_Dev.uproject` in UE 5.5 and rebuild modules when prompted

Command-line build (UE 5.5):

```
<UE_5.5>\Engine\Build\BatchFiles\Build.bat LoadingFX_DevEditor Win64 Development -Project="<repo>\LoadingFX_Dev.uproject" -WaitMutex
```

Plugin compile check (any engine from 5.5 to 5.8). Keep `-Package` short, such as `%TEMP%\lfxbp\5.8`: under a long directory UBT fails on Intermediate paths over 260 characters.

```
<UE_5.x>\Engine\Build\BatchFiles\RunUAT.bat BuildPlugin -Plugin="<repo>\Plugins\LoadingFX\LoadingFX.uplugin" -Package="<short dir>" -TargetPlatforms=Win64 -Rocket -unattended -utf8output -nop4
```

### Linux cross-compile (set up 2026-11-01)

Epic's cross-toolchains are installed under `C:\UnrealToolchains`: `v23_clang-18.1.0-rockylinux8` for 5.5 and `v26_clang-20.1.8-rockylinux8` for 5.7 and 5.8 (5.6 wants v25, not installed; each engine names its version in `Engine/Config/Linux/Linux_SDK.json`). UBT reads `LINUX_MULTIARCH_ROOT` first and, only when it is unset, the in-tree path `<Engine>\Engine\Extras\ThirdPartyNotUE\SDKs\HostWin64\Linux_x64\<version>`; a junction to the matching toolchain sits there in 5.5, 5.7 and 5.8, so every engine finds its own version as long as the variable is not set in the process. The v26 installer set it at machine level, and `ValidatePlatforms` does not check the version (5.5 accepts the v26 path), so remove it from the process before building (`Remove-Item Env:LINUX_MULTIARCH_ROOT` in PowerShell) or delete it at machine level. `UnrealBuildTool.exe -Mode=ValidatePlatforms -Platforms=Linux` (with `DOTNET_ROOT` at the engine's bundled dotnet under `Engine\Binaries\ThirdParty\DotNet`) reports VALID on all three. The toolchain alone is not enough: `BuildPlugin` filters `-TargetPlatforms` through `InstalledPlatformInfo.IsValidPlatform`, which needs the Launcher's Linux target platform (`Engine\Binaries\Linux\UnrealGame.target` and the precompiled Linux libs; Library > engine > Options > Target Platforms > Linux, about 15 GB on disk per engine), and drops a platform that is not installed without any message, so without it `-TargetPlatforms=Linux` prints BUILD SUCCESSFUL and compiles nothing. Added to 5.5.4 and 5.8.4 on 2026-11-01 (5.6 and 5.7 still lack it). `-NoHostPlatform` skips the editor build. A platform must also be in each module's `PlatformAllowList` for anything to compile (Linux is since 2026-11-01; the first runs that day used a copy under `%TEMP%\lfxsrc\LoadingFX` with the lists removed, and Fab requires an allow or deny list per module, so the list is never dropped). Result: BuildPlugin passed on 5.5.4 (clang 18.1.0) and 5.8.4 (clang 20.1.8) for UnrealGame Linux Development and Shipping, 15 files per configuration, with no compiler or UHT warning, about 3 minutes each (about 1 minute once the engine side is warm); the real `LoadingFX.uplugin` with Linux in its allow lists passed the same way on both. A game-target build leaves no `Binaries\Linux` in the package (the modules are precompiled into `Intermediate\Build\Linux\x64\UnrealGame\<Config>\<Module>\*.o` plus a `.precompiled` manifest); the proof that something was built is those files and the `Using toolchain` / `[n/15] Compile` lines in the log.

### UE 5.8 workbench and live editor access (set up 2026-10-25)

UE 5.5 has no MCP server (the engine's `ModelContextProtocol` plugin and its `ToolsetRegistry` arrive later and depend on modules 5.5 lacks, and they are NoRedist engine code, so they cannot live in this public repository). The work that wants MCP runs in a second checkout opened with UE 5.8; the 5.5 editor is reached through the Python plugin's remote execution.

- **Workbench:** a git worktree on branch `workbench/ue58` next to this checkout (`..\LoadingFX_Dev_UE58`), opened with `powershell -ExecutionPolicy Bypass -File Tools\Open-Workbench.ps1` (`-Build` compiles the editor target with 5.8 first, needed after C++ changes). The script starts UE 5.8 with `-EnablePlugins=ModelContextProtocol,AllToolsets -ModelContextProtocolStartServer`, so the `.uproject` stays as it is. The server listens on `http://127.0.0.1:8000/mcp` (55 toolsets, reached through `list_toolsets` / `describe_toolset` / `call_tool`), and an `.mcp.json` in both checkouts (ignored by git; Claude Code reads it at session start) points there. The worktree has its own Binaries, Intermediate and DDC. Use it to explore and draft: inspect assets, try a material change live, draft Blueprints and widgets, Slate Inspector, automation tests. Commit only text from it (C++, Python, docs).
- **Content saved there is 5.8-only** (`FileVersionUE5` 1018 from 5.8.3, against 1013 from 5.5), and nothing converts it back. A material change goes into its builder script and is regenerated with UE 5.5 here. A Blueprint or widget drafted there is exported as text with `Plugins/DevSampleTools` and rebuilt in 5.5 by its `build_sample.py` (see Dev-only tooling).
- **MCP in practice (2026-10-25):** the server must be up when the Claude Code session starts; one started later stays failed in that session (reconnect it with `/mcp`, or post JSON-RPC to `http://127.0.0.1:8000/mcp` directly: `initialize`, then `tools/call` with `call_tool`). What drafting uses: `UMGToolSet` (`CreateWidgetBlueprint`, `AddWidget`, `ToggleWidgetAsVariable`, `BindToEventProperty`, `CompileWidgetBlueprint`), `BlueprintTools` (`add_variable`, `find_node_types` / `get_node_type_pins` for node ids and pin names, `write_graph_dsl` / `read_graph_dsl`, an S-expression DSL whose reference `get_graph_dsl_docs` returns), `ObjectTools.set_properties` on widgets, slots and the CDO (partial struct JSON keeps the other fields), `AssetTools.save_assets`, and for levels `SceneTools` (`load_level`, `add_to_scene_from_asset` / `_from_class`, `find_actors`), `ActorTools` (`set_label`, `look_at`, `set_actor_transform`) and `EditorAppToolset.CaptureViewport` / `CaptureEditorImage` (a PNG in the result's `returnValue`) to look at the result. No tool creates a level (use `LevelEditorSubsystem.new_level_from_template` in Python) or exports copy text, hence `DevSampleTools`. Pitfalls found while drafting the sample:
  - `add_object_variable` with `/Script/Engine.World` made an `int` variable, and Python cannot set `EdGraphPinType` fields: variable types are written as `replace_member_variables` text instead.
  - `write_graph_dsl` only writes into events that exist; a custom event is `Custom|Name` and gets no parameters (no tool adds them), so anything with parameters is a function (`add_function_graph` + `add_function_param`, compiled before the DSL sees it), and a latent node (Delay) goes in a parameterless custom event fed by a variable. Into an existing function graph the DSL appends and leaves the old nodes behind, disconnected: delete everything but the entry and result nodes first. Removing and adding a function again renames it (`AddLog_0`), because the compiled class still has it.
  - Some node ids are shared by several functions, and the DSL takes the wrong one: `Rendering|Material|Set/GetScalarParameterValue` and `SetVectorParameterValue` resolve to the Material Parameter Collection versions. Place such a node with `create_node` and `declaring_class` (`/Script/Engine.MaterialInstanceDynamic`) and wire it with `connect_pins`. The DSL also cannot set Create Event's function (connect its output first, then `set_create_event_function`) or see Create Widget's Expose on Spawn pins (connect them afterwards), and `"\n"` becomes a backslash and an n (`set_pin_value` with a real line break). A function of another Blueprint is `Class|<class name without underscores>|Name`; a positional argument to a call goes to `self`, so pass arguments by name.
  - The first `CreateWidgetBlueprint` after an editor start failed with "the path already exists" (an empty package left in memory); Python's `create_asset` worked.
  - The editor's Python keeps globals and modules between `ue_exec.py` commands: a `UWorld` left in a global made the next `load_level` fail with "World Memory Leaks" (a fatal error), so run code inside functions, and `importlib.reload` a shared module after changing it.

  For Python in the workbench, copy `Config/UserEngine.ini` there (ignored by git) and pass `--project-root <workbench>` to `Tools/ue_exec.py`. The workbench also needs `Plugins/DevSampleTools` (compile with `Open-Workbench.ps1 -Build`); until the branch that adds it is merged into `workbench/ue58`, it is an untracked copy there, which has to be deleted before that merge.
- **pre-commit hook** (`Tools/GitHooks/pre-commit`, installed into the repository's common `.git/hooks`, so it covers every worktree): rejects a staged `.uasset` / `.umap` whose `FileVersionUE5` is above 1013, reading LFS-tracked content from the local object store. Checked on 2026-10-25 with a material saved by 5.8.3 in the workbench, and in throwaway repositories with and without LFS. After a fresh clone, install it again: `cp Tools/GitHooks/pre-commit "$(git rev-parse --git-common-dir)/hooks/pre-commit"`.
- **5.5 live access:** `Config/UserEngine.ini` (per user, ignored by git, a config layer above `DefaultEngine.ini`) sets `bRemoteExecution=True` for the Python plugin, which listens on the local host only (bind 127.0.0.1, TTL 0). `Tools/ue_exec.py` (any Python 3; it loads the engine's own `remote_execution.py`, found through the Epic Games Launcher's install list) runs a file with arguments, `-c` code (`-c -` reads stdin) or a `-e` expression in the 5.5 editor that has this checkout open. It prints the output in order, with warnings marked `[Warning]`, and exits with 1 when the command fails. A builder runs in the open editor in seconds, with its `[TEST]` lines on stdout: `python Tools/ue_exec.py Plugins/DevMaterialTools/Tools/build_m_loadingarc.py`. `--wait 300` waits for an editor that is still starting. The script replaces the engine client's receive loop, which stops at the first short `recv()` and so cut long results (checked with a 1.4 MB result). The editor runs the command on its game thread, so it does not answer anything else meanwhile, and every log line costs it about 15 ms. Viewport screenshots did not come out this way (`HighResShot` and `AutomationLibrary.take_high_res_screenshot` wrote nothing); use the `LFXProto` screenshots in `-game`. The editor's own windows do: the console command `EditorShot All` (through `SystemLibrary.execute_console_command`) reads every visible editor window back through Slate, also from behind other windows, and writes one BMP each to `Saved/Screenshots/WindowsEditor`. A maximized main window comes with an 8 px black border. Python opens an asset's editor (`AssetEditorSubsystem.open_editor_for_assets`), but not Project Settings, a palette category or a Blueprint's Graph mode, and a graph opens unfitted.

## Architecture

| Module | Type | Role |
|--------|------|------|
| `LoadingFX` | Runtime | Spinner Slate/UMG widgets, the loading icon subsystem, blocking-load rendering (MoviePlayer). Excluded from Server targets. |
| `LoadingFXLoader` | Runtime | Lightweight async/sync asset loader subsystem. No UI dependency. |
| `LoadingFXBridge` | Runtime | Optional glue: forwards loader events to the loading icon. Excluded from Server targets. |

**Dependency rule:** `LoadingFX` and `LoadingFXLoader` must never depend on each other. Only `LoadingFXBridge` depends on both.

### Dev-only tooling

`Plugins/DevMaterialTools/` is a local editor plugin (not distributed, excluded from the release zip, not listed in the `.uproject`). It exposes Named Reroute / comment helpers to Python (`unreal.DevMaterialTools`). Its `Tools/` scripts build the material assets from scratch. Always run them with UE 5.5 (see its README); `build_all.py` rebuilds everything in dependency order. To change a material, edit its builder script and regenerate. Don't hand-edit the generated asset.

The current materials (`M_LoadingDotRing`, `M_LoadingDotGrid`, `M_LoadingBoxes`, `M_LoadingSpokes`, `M_LoadingArc`, `M_LoadingComet`, `M_LoadingDotRow`, `M_LoadingDualArc`, `M_LoadingSegments`, `M_LoadingTimer`, `M_LoadingHourglass`, `M_LoadingBounce`, `M_LoadingRipple`, `M_LoadingEqualizer`, `M_LoadingGooey`, `M_LoadingMorph`, `M_LoadingLine`, `M_LoadingChase`, and the bars `M_LoadingBarSlide`, `M_LoadingBarStripes`, `M_LoadingBarFill`) follow the material contract below. The first three were ported from the sandbox project; `M_LoadingSpokes` was ported from the user's Shadertoy with the AA width taken from `fwidth(d)` (DDX/DDY of the distance field) instead of `PixelSize`, which is only valid when `d` is continuous across cells (every bar has the same shape). `M_LoadingArc` (one rounded arc that stretches and shrinks while it turns) was designed here: the look was approved from stills rendered in Python with the same formulas, and the shape is iq's `sdArc` (loop-free and branch-free; `Step` + `Lerp` select the end cap). It has two rates: `Speed` (steady rotation, rev/s) and `StretchSpeed` (grow/shrink cycles per second). With the defaults (0.3, 0.75) each cycle advances about 1.02 turns, so every stretch starts near 12 o'clock. `M_LoadingComet` (a round head with a tail that thins and fades over one turn) was ported from the user's sandbox `M_Loading_Icon_UI`. The original faded the tail by darkening its color while its centerline alpha stayed 1, so a dark full circle showed on light backgrounds; the port fades opacity instead. It also adds a round head cap whose diameter covers the `frac` wrap, so `max(tail, cap)` is continuous there, and uses real time (the original's `TimeWithSpeedVariable` uses GameTime). `M_LoadingDotRow` (a row of `Count` dots that swell and brighten in turn, left to right; chosen from the Canvas design previews) finds the nearest dot from `p.x` and evaluates one circle, which is exact while `DotRadiusMax <= Spacing / 2`. Its radii differ per dot, so the AA width is `PixelSize`. Raising `Count` needs a smaller `Spacing`, or the row leaves the widget. `M_LoadingDualArc` (two pairs of opposite arcs, the outer pair clockwise and the inner pair the other way) is one color by the user's choice (the design preview drew the inner pair in `SecondaryColor`). Folding both axes with `abs` lands the opposite arc on the first, so each ring is one `sdArc` (valid while `Arc <= 0.5`); the rings merge with `min` before anti-aliasing. `Speed` is the outer ring's rate and `InnerSpeedRatio` (default -1.3) scales it for the inner ring, so `Speed` alone sets the tempo. `M_LoadingSegments` (a ring of rounded segments that fill clockwise one at a time, then drain in the same order; from the second round of design previews) draws the pixel's own segment with the same `sdArc` (every segment has the same shape, so `d` is continuous). The lit segments are the window `k - Count + 1 .. k`, where `k` steps through `2 * Count` steps per cycle, so filling and draining need no branch. `Gap` is the space between rounded ends in `P` units along the ring. `M_LoadingTimer` (a pie that fills and empties inside a thin ring; same round of previews) draws the pie with iq's `sdPie`, its edges moved by the same two `smoothstep` curves as Arc. A pie or gap thinner than a pixel is a zero-distance line that SDF anti-aliasing draws at half coverage, and `smoothstep` lingers near full and empty, so a hairline at 12 o'clock stayed for over 0.1 s (seen in the Gallery). The material fades a pie that is thinner than a pixel at its rim, and closes a gap that is thinner than a pixel toward the full disc. Keep that in mind for any shape that can shrink below a pixel. `M_LoadingHourglass` (sand runs out, then the glass turns over clockwise) was first written as a Shadertoy GLSL sketch and checked in WebGL2 (a harness page under `Saved/`, opened in the built-in browser from inside the project folder; files outside it only render as static snapshots). Folding both axes reduces the frame to one slanted side and one cap (`MF_SdSegment2D`, iq's `sdSegment`, built by the same script). The bulbs are nearly triangles, so the top surface and the bottom surface share one height, `(HalfHeight - inset) * sqrt(1 - flow)`. The falling stream is drawn at least one pixel wide at proportionally lower opacity (the Timer lesson). `Neck` must stay well above `Thickness / 2`, or the sides meet in an X. `M_LoadingBounce` (a ball that bounces and flattens on landing, with a shadow that shrinks and fades as the ball rises) splits each cycle into `ContactFraction` on the floor and the flight. The height is a parabola in time over the flight and 0 on the floor without a branch. The ball only flattens while it touches the floor; the design preview squashed it in the air. The ball and the shadow use `MF_SdEllipse2D` (iq's ellipse approximation, built by the same script), whose `k0 / k1` is clamped between the two radii so the exact center reads `-min(R)` instead of `0 / 0`. The shadow is kept at least one pixel thick at proportionally lower opacity. `M_LoadingRipple` (rings start at the center, slow down as they spread to `Radius` and fade out; from the third round of design previews, 2026-10-14) has `Count` rings evenly spaced in time: ring `k` has the phase `(k + s) / Count`, `s = fract(Time * Speed * Count)`, so `Speed` is spreads per second (each ring lives `1 / Speed` s) and a negative `Speed` closes the rings in. The radius is `Radius * g(phi)`, `g(phi) = 1 - (1 - phi)^Easing`. Inverting `g` at the stroke's inner edge, `rho - (th - aa) / 2`, gives the innermost ring whose stroke reaches the pixel; it and the ring inside it are the only two drawn. With `Easing` above 1 the rings bunch up near `Radius` and may overlap, and a ring fades as it spreads, so the innermost covering ring is the brightest: the two match the max over all rings while neighbors stay a pixel apart (checked against a brute-force loop in the WebGL2 sketch: no difference with the defaults from 32 to 512 px; extreme values such as `Count` 8 with `Easing` 3 in a small widget lose part of a faint AA edge at the rim). Inverting at the ring centers instead missed a brighter overlapping ring with `Count` 5 at every size (up to 0.1 opacity), where the edge version differs only at 32 px. `M_LoadingEqualizer` (a row of `Count` rounded bars that grow and shrink around the center line in turn, left to right; the same round of previews) takes the layout and timing of Dots (`Count`, `Spacing`, `Speed`, `Stagger`, `PulseWidth`), with `PulseWidth` 1 by default for a continuous wave. `HeightMin` / `HeightMax` are half heights to the tip of the rounded end. Every bar has the same width, so the nearest bar alone is exact while `Thickness < Spacing`; the heights differ, so the AA width is `PixelSize`. `M_LoadingGooey` (droplets bud off a round core, drift out to `Radius` while the whole turns clockwise, then melt back in; the same round) joins the core and the droplets with iq's polynomial smooth min. `Speed` turns it and `SpreadSpeed` is the out-and-back rate. Each pixel uses only the two droplets around its angle, so `Count` is a parameter and there is no loop: on a droplet's axis the pairs on both sides mirror each other, so the field stays continuous. Compared in the WebGL2 sketch, it looks like the design preview's smooth min over every droplet, but the merged blob keeps its size for any `Count` (over every droplet it grows with `Count`); joining the pair with a hard `min` showed corners in the necks. With `Count` 1 the droplet would be joined with itself and grow by `Smoothness / 4`, so `Count` is 2 or more. A smooth-min field is not a distance (its gradient drops below 1 in the necks, where `PixelSize` blurs the edge), so the AA width is the length of its screen gradient, `length((ddx(d), ddy(d)))`. `M_LoadingMorph` (a rounded square turns a quarter clockwise, rounds off into a circle halfway through, then pauses; the same round) draws `MF_SdRoundBox2D`. A square looks the same after a quarter turn, so the angle is just `e * 90` degrees with `e = smoothstep(0, TurnFraction, fract(Time * Speed))`, and `Sine` / `Cosine` with `period` 4 take `e` directly. The corner radius peaks halfway through the turn (`Roundness` 1 = a circle), which also keeps the turning corners in: at most 0.786 along x or y, against 0.964 for a square that stays square (`Roundness` 0). `M_LoadingLine` (an indeterminate progress bar: a bar grows from the left end of a faint track and leaves at the right end; the first of the fourth round of design previews, 2026-10-16) draws the track and the bar as horizontal capsules, `length((p.x - clamp(p.x, x0, x1), p.y)) - r`, and cuts the bar to the track with `max`. The preview moved both ends with `smoothstep` and overshot the track, so nothing showed for about a third of every cycle. The head now eases out over `1 - TailDelay` and the tail eases in after `TailDelay`, both between the points where the bar's round end touches the track's end from outside (`±(HalfWidth + Thickness / 2)`), so there is no gap (compared cycle by cycle in `Saved/LinearHarness`). Where the bar only touches the track, SDF anti-aliasing draws a half-coverage dot (the Timer lesson), so both ends cross the track's ends at full speed; an end that slows down there leaves the dot behind. Like every spinner it keeps its size in a wide widget instead of filling the width. `M_LoadingChase` (`Count` dots chase each other clockwise around a ring, slowing down and bunching up at 12 o'clock, where they melt into one blob, and pulling apart as they speed through 6 o'clock; from the third round of design previews, shown again in the fourth; the melting was the user's idea, 2026-10-17) places dot `i` at the angle `TAU * u - Easing * sin(TAU * u)`, `u = fract(Time * Speed - i * Stagger)`, and joins the dots with iq's polynomial smooth min (`Smoothness`, 0 = separate dots). Smooth min feels every dot within reach, and three to five are within reach where the dots bunch up, so the material unrolls eight dots and joins them all; `Count` (1 to 8) hides the rest by raising their distance by 10. A first version drew only the two dots around the pixel's angle, found by solving Kepler's equation `x - Easing * sin(x) = M` with two Halley steps from `M + Easing * sin(M)` (at most 1.1e-6 of a lap off at `Easing` 0.85): exact for a plain `min` (checked against every dot), but joined with smooth min it showed steps in the blob, and a four-dot version that faded the outer two still left dents (`Saved/ChaseHarness/smin.html`). Smooth min commutes with a shift, so `DotRadius` comes off once after the chain, and the AA width is the length of the screen gradient, as in Gooey. The melted blob reaches past `Radius + DotRadius`, so `Radius` is 0.672 for a footprint of 0.8005 (0.762 with the dots apart).

**Loading bars (decided 2026-10-16; built and checked in UE 5.5 on 2026-10-22).** Surveyed first: Epic's own loading screens (Lyra's CommonLoadingScreen) and the most used free plugin (AsyncLoadingScreen) show no progress for map loads, because the engine reports none (`GetAsyncLoadPercentage` returns -1 on the UE5 loader, World Partition has no hook, and a blocked game thread cannot update a widget on the MoviePlayer screen). Real progress exists only for asset-level loads (`FStreamableHandle::GetProgress`, what `ULoadingFXLoaderSubsystem` reports) and PSO precaching. So 1.0 ships indeterminate bars plus a progress bar for the loader, and the docs say so. `MF_SpinnerCoords` gained a third output, `Extent = m / fw` (the widget's half extents in `P` units: 1 on the shorter side, the aspect ratio on the longer), so a bar can span the widget while `P` stays isotropic and `PixelSize` stays valid. Every bar is one horizontal capsule, inset by `1 - Thickness / 2` on all sides: `R = Thickness / 2`, `L = max(Extent.x - 1, 0)`, `dTrack = length((max(abs(p.x) - L, 0), p.y)) - R`. With `Thickness` 1.6 it reaches ±0.8 (the reference circle) and leaves 0.2 at the ends; 2 fills the widget; a square widget gives a circle. `TrackOpacity` (0.25) dims the track. `M_LoadingBarSlide` (indeterminate, Material Design style): `head = smoothstep(0, 1 - Lag, u)`, `tail = smoothstep(Lag, 1, u)` (Arc's two ramps) give the segment `xA..xB`; `dSeg = max(dTrack, max(xA - p.x, p.x - xB))` (an intersection of SDFs stays 1-Lipschitz, so the AA width is `PixelSize`), and `fade = saturate((xB - xA) / aa)` removes the hairline at the wrap (the Timer lesson). `TailDelay` 0.35 makes the segment about 70 % of the track at most, 0.5 the whole track. `M_LoadingBarStripes` (indeterminate, barber pole): `t = (p.x - p.y) / Period - Time * Speed` leans the stripes like `/`; `dt = abs(fract(t) - 0.5) - Duty / 2` is a triangle wave (continuous at the wrap), and one pixel in `t` units is `aa * sqrt(2) / Period`. `M_LoadingBarFill` (determinate): `xF = lerp(xL, xEnd, saturate(Progress))`, `dFill = max(dTrack, p.x - xF)` (a flat edge: a rounded head would become a shrinking dot near 0), the same hairline fade near 0, and a sheen `smoothstep(0, 1, saturate(1 - abs(p.x - sx) / SheenWidth))` sweeping from outside the left end to outside the right, which pushes the filled part toward white (`SheenStrength` 0.5) so coarse loader progress still shows motion. The sheen is invisible while `PrimaryColor` is white (`LFXProto.ProgressBar` tints one bar to review it). `Progress` defaults to 0.65 in the asset for the thumbnail. Checked in a WebGL2 sketch (`Saved/BarHarness/harness.html`, rendered headlessly with Playwright and Chromium at six sizes) before the builders were written. Contract clause: a determinate material reads the scalar parameter `Progress` (0..1) and saturates it; nothing else in the library takes input. Widget: `ULoadingFXProgressBar` (UMG "LoadingFX Progress Bar", derived from `ULoadingFXSpinner`, whose `ResolveMaterial` / `ApplyMaterial` / `GetDynamicMaterial` became virtual for it) draws through a dynamic instance held in the transient `ProgressMaterial`, never in `Material` (`UMaterialInstanceDynamic::Create` makes a transient object, and a widget blueprint saved with one in `Material` would lose its material); empty `Material` means `M_LoadingBarFill`, which `OnModifyCook` adds to every cook. `SLoadingFXProgressBar` writes `Progress` on the instance: an increase is interpolated linearly over `SmoothingTime` (0.25 s) on a Slate active timer registered only while in flight, a decrease is applied at once (a bar reset for the next load never runs backwards). Blueprint usage: Load Assets Async → On Progress → Set Progress; no C++ glue between the loader and the bar. Separate materials rather than one with a `Progress < 0` indeterminate mode: both paths would run per pixel, and the icon subsystem cannot set parameters, so the indeterminate side would be unusable as the icon; the indeterminate bars work as the loading icon with a wide `IconSize` (192x12, say). 2026-10-22, UE 5.5: `build_all.py` passed for every script (the `Extent` output changes every material's function call, so `build_proto_gametime_variant.py` must be run again too, or the GameTime row in `LFXProto.Gallery` stays blank), and `LFXProto.Showcase ref` (bar tiles drawn 4:1), `LFXProto.Gallery` and `LFXProto.ProgressBar` looked as designed. ## Confirmed Design Decisions

### Loading icon (display — the main feature)

- Spinners are procedural (SDF) materials, and many are bundled. The loading icon uses a **project-wide default only** (Project Settings). There is no per-request override and no runtime switching API.
- The loading icon subsystem is a `UGameInstanceSubsystem`. Show and hide use handle-based reference counting (`Acquire(Reason)` / `Release(Handle)`), with optional auto-release when a weakly referenced owner is destroyed.
- The icon is added with `UGameViewportClient::AddViewportWidgetContent` so it survives map travel. Do not use `AddToViewport`, because those widgets are removed on world teardown.
- The icon must keep animating during blocking loads, which requires MoviePlayer. MoviePlayer is unavailable in PIE, so the icon freezes there; document this behavior.
- **v1 scope:** if the icon is visible when LoadMap starts, automatically switch to blocking rendering (`PreLoadMap` / `PostLoadMapWithWorld`). It does **not** auto-show the icon or decide when travel is complete. Map transition management is postponed; users build it with show/hide.
- The spinner is also provided as a standalone UMG widget, and the materials must work on their own on a plain UMG `Image`. Only the subsystem's icon keeps spinning during blocking loads; spinners placed in user widgets do not.
- **Implemented:** `ULoadingFXIconSubsystem` (`Acquire` / `Release` / `ReleaseAll`, `IsHandleActive`, `OnVisibilityChanged`; owner auto-release is polled by a core ticker that runs only while owned requests exist; the viewport widget is created lazily and also on `UGameViewportClient::OnViewportCreated`, because the game viewport is created after the game instance) and `SLoadingFXSpinner` (leaf Slate widget drawing a material brush, to be reused by the UMG widget). The MoviePlayer takeover is `HandlePrepareLoadingScreen`; it checks `LoadingScreenIsPrepared()` first, so a loading screen set up by someone else wins. Console: `LoadingFX.Icon.Show` / `Hide` / `Dump`.
- **Implemented (UMG):** `ULoadingFXSpinner` wraps `SLoadingFXSpinner`. Properties use `BlueprintGetter` / `BlueprintSetter` so Blueprint sees one Get/Set pair each. `Material` empty means the project's loading icon material, resolved in `ResolveMaterial` (the result is held in the transient `DrawnMaterial` so the fallback stays referenced). `GetDynamicMaterial` follows `UImage`: the dynamic instance replaces `Material` on that widget. Verified at runtime with `LFXProto.UmgSpinner shot quit` (no widget blueprint; the widgets are created with `NewObject` and hosted through `TakeWidget`).
- **Implemented (preload):** `Initialize` starts `FSoftObjectPath::LoadAsync` for the effective `LoadingIconMaterial` (a material already in memory, as in the editor, is taken directly; `FindObject` skips objects still being async loaded). The result is held in the `IconMaterial` UPROPERTY. If the material is needed while the preload is still in flight (an `Acquire` during startup, or a blocking load that starts that early), `GetIconMaterial` waits for that one request with `FlushAsyncLoading(RequestId)`, which also runs the completion delegate, so the icon still appears at once. Decided over "show the icon when the material arrives" because MoviePlayer needs a drawable widget at the moment `OnPrepareLoadingScreen` fires, and the wait is at most what is left of one small package. A missing or wrong-typed material logs one warning at load time and the icon draws nothing. Checked with `LFXProto.Preload` (see Verification Prototype). In uncooked processes with MoviePlayer (`-game`), `SetIconMaterial` (and `SetUpIconLoadingScreen` again, a no-op once complete) also calls `UMaterialInterface::EnsureIsComplete`, which compiles the material's missing shaders and waits for them (issue #5, see Findings); it is compiled out of cooked builds, and skipped without MoviePlayer (editor, PIE), where every draw is on the game thread.
- **Implemented (show delay):** `ULoadingFXSettings::IconShowDelay` (seconds, default 0.5, 0 = none). The first `Acquire` while the icon is hidden starts the delay; more requests do not move it. A core ticker, registered only during the delay, shows the icon when `FPlatformTime::Seconds()` reaches the deadline. Releasing every request within the delay cancels it, and the icon never appears. `IsIconVisible` / `OnVisibilityChanged` follow what is on screen, so they report the icon only once it appears (`GetRequestCount` still counts the waiting requests). A blocking load that starts within the delay is taken over by MoviePlayer at once (otherwise a long load would freeze the last frame with no icon), but the loading screen's icon stays hidden until the deadline: its `SBox` visibility is a lambda over copied values, evaluated in MoviePlayer's Slate prepass on the loading thread (`SWidget::Prepass_ChildLoop` updates visibility attributes), and logs once when it appears. The screen still turns black (`LoadingScreenBackgroundColor`) at once, as it does for any takeover. The icon's display time counts from the deadline, not from when the game thread shows it, because after a blocking load it has been on the loading screen since then. A last release after the deadline that comes before the ticker ran (from inside LoadMap, for example `BeginPlay` or `PostLoadMapWithWorld`) first shows the icon as of the deadline, then applies the minimum display time. The setting is read at each first request. Checked with `LFXProto.ShowDelay`.
- **Implemented (minimum display time):** `ULoadingFXSettings::IconMinimumDisplayTime` (seconds, default 1, 0 = none), counted from the moment the icon appeared (the end of the show delay). When the last request goes sooner (`Release`, owner auto-release, and also `ReleaseAll`), the icon stays until that time is over. A core ticker, registered only for that hold, compares `FPlatformTime::Seconds()` with the deadline, so it runs while the game is paused and across travel, and the time of a blocking load counts. `IsIconVisible` / `OnVisibilityChanged` follow what is on screen: still visible during the hold. An `Acquire` during the hold only cancels it (no hide/show pair, and the time still counts from the first show). A blocking load that starts during the hold is taken over by MoviePlayer as usual, because the icon is on screen and would freeze there otherwise. The setting is read at each last release, so editor changes apply at once. Checked with `LFXProto.MinDisplay`.
- **Z-order (decided 2026-10-30):** `IconZOrder` defaults to 10010 (it was 1000), just above TransitionFX's widget-layer transitions (`UTransitionPreset::WidgetZOrder` 10000, added with `AddViewportWidgetContent` as is), so the icon shows over a screen TransitionFX holds covered while loading, with no setting to change when the two plugins are used together. The prototype's overlays (`LoadingFXProto::ViewportOverlayZOrder` 10000 to 10002) now sit below the icon.
- **Implemented (background color, 2026-11-01):** `ULoadingFXSettings::LoadingScreenBackgroundColor` (category "LoadingFX|Loading Screen", default black, `HideAlphaChannel`). `MakeLoadingScreenWidget` puts the icon widget over a full-screen `SImage` with `FCoreStyle`'s `WhiteBrush` tinted by it, only for the MoviePlayer instance (the viewport icon has no background). The color sits outside the show-delay visibility lambda, so the screen changes the moment MoviePlayer takes over, as the black did, and the icon appears at the deadline. Alpha is forced to 1: MoviePlayer keeps only its own black behind the widget, so a translucent color would only darken toward black. The setting is read at each takeover. Checked in 5.5 `-game` with `LFXProto.IconTravel ... cold` and `... cold bg`: 238 of 238 loading screen frames read back as sRGB (0, 0, 0) and (40, 70, 140) exactly, and the icon was on 214 of 214 frames after the show delay in both runs. BuildPlugin passed on 5.5 – 5.8 (and Linux on 5.5 and 5.8) with no compiler or UHT warning. Decided over fades for now: a fade-in after the load is possible (a viewport overlay of the same color that fades once MoviePlayer stops), but a fade-out before the load cannot be automatic, because the plugin learns of a map load only when the game thread is already blocked.

### Material contract

- The time source is the `Time` node with **Ignore Pause enabled** (real time), so spinners keep animating while the game thread is blocked (confirmed, see Verification Prototype). No external time path is needed.
- Multiply the final output by `VertexColor` (UMG `ColorAndOpacity`, `RenderOpacity` and fades arrive through it): Emissive = `PrimaryColor.rgb * VertexColor.rgb`, Opacity = `coverage * PrimaryColor.a * VertexColor.a`.
- Use common parameter names across all spinners (e.g. `PrimaryColor`, `SecondaryColor`, `Speed`, `Thickness`). `Speed` is in cycles per second (revolutions per second for rotating spinners); positive turns clockwise.
- **Parameter vocabulary (unified 2026-10-22):** `Count`; `Radius` is the centerline radius of a ring layout; `Thickness` a stroke width; `Spacing` center to center; `DotRadius` / `DotRadiusMin` / `DotRadiusMax` a dot's radius (fixed / at rest / at the peak); `Half*` half extents; `*Opacity` the opacity of an accessory (track, ring, shadow) and `OpacityMin` / `OpacityMax` the faintest / brightest element; `Stagger`, `PulseWidth`, `TailDelay`, `*Fraction` are fractions of a cycle; `Easing` / `Smoothness` are shape and motion coefficients. New parameters follow the form `Noun` + `Min` / `Max`.
- **Parameter groups:** every parameter sits in one of `Appearance` (`PrimaryColor` and every opacity / look parameter), `Shape` (layout and sizes) or `Motion` (`Speed` and every timing parameter); a determinate material adds `Input` (`Progress`). The builders write the order Input, Appearance, Shape, Motion into the material's `ParameterGroupData` through `DevMaterialTools.set_parameter_group_sort_priorities` (`UMaterialEditorOnlyData` is not exposed to Python), so the material instance editor shows the sections in that order; within a group the sort priorities run from 0 (`Count` / `Radius` / `Spacing` first, then `Thickness` / `DotRadius*`; `Speed` first in Motion; `PrimaryColor` first in Appearance). A new builder declares `PARAM_GROUPS` (parameter → group) and the `[TEST]` checks every parameter's group and the written order.
- **Default footprint:** with default parameters a ring layout touches the reference circle of radius 0.8 (`P` units: 1.0 = the widget edge on the shorter side) and a grid layout touches the reference square of half-width 0.72 (keyline, 0.9 × 0.8, so circles and squares look the same size), measured at the largest moment of any pulse. The margin keeps pulses and the anti-aliased edge off the widget border. Per material: DotRing `Radius + DotRadiusMax = 0.8`, Spokes and DualArc `OuterRadius + Thickness / 2 = 0.8`, Arc, Comet, Segments and Timer `Radius + Thickness / 2 = 0.8`, Chase 0.8 at the most melted moment (`Radius + DotRadius = 0.762` with the dots apart), Ripple the same as its rings vanish, Equalizer `(Count - 1) / 2 * Spacing + Thickness / 2 = 0.72` across and `HeightMax = 0.72` at the peak, Line `HalfWidth = 0.72` across, Gooey `Radius + DropletRadius = 0.8` at full spread, Morph `HalfSize = 0.72` at rest (0.786 at most while it turns), DotGrid `Spacing + DotRadiusMax = 0.72`, DotRow `(Count - 1) / 2 * Spacing + DotRadiusMax = 0.72`, Boxes `BoxSize + BoxGap / 2 = 0.36` in its half-scale `p`, Hourglass `HalfHeight + Thickness / 2 = 0.72` at rest, Bounce `Floor + BounceHeight + 2 * BallRadius = 0.72` at the top of the bounce and `Floor - ShadowGap - ShadowHeight = -0.715`. A shape that turns over may leave the keyline while it turns, but not by much: unshrunk, the hourglass would reach 0.946 along x or y at 45 degrees, so it shrinks by `FlipShrink` (0.3) and reaches at most 0.794. Check with `LFXProto.Showcase ref`.
- A spinner must look complete with default parameters and must not break when drawn at a non-square size. Build coordinates with `MF_SpinnerCoords`: `P` is centered and y-up, and the shorter side spans -1..1, so the shape stays round and centered. `PixelSize` is one screen pixel in `P` units, for anti-aliasing. `Extent` is the widget's half extents in `P` units, for shapes that span the widget (the bars). It derives the widget size from UV screen derivatives, so no size parameter is needed.
- **Bars** span the widget: a horizontal capsule inset by `1 - Thickness / 2` on every side (`Thickness` 1.6 touches ±0.8 on the short side and leaves 0.2 at the ends; 2 fills the widget), drawn in a wide widget such as 320x16. A square widget gives a circle.
- **Progress (determinate input):** a material that shows progress reads the scalar parameter `Progress` (0..1) and saturates it. `ULoadingFXProgressBar` writes it on a dynamic instance; the loading icon never sets parameters, so a determinate material is not for `LoadingIconMaterial`.

### Asset loader (secondary feature)

- It handles generic async and sync asset loading only.
- Sync loads broadcast begin/end events so the Bridge can switch the icon to blocking rendering.
- **API shape (decided 2026-10-12, implemented the same day):**
  - The loader is a `UGameInstanceSubsystem` (like the icon subsystem, so the Bridge finds both in one game instance and PIE instances stay apart) with its own `FStreamableManager`.
  - **Requests:** Blueprint takes `Assets` (array of soft object references) and `Classes` (array of soft class references). An array of soft references to a subclass connects to these pins (the K2 schema compares soft pin types with `IsChildOf`). C++ also takes `FSoftObjectPath` arrays. Results come back in input order (`LoadedAssets`, `LoadedClasses`), null where a load failed, with one warning. Primary asset IDs are left to the engine's AssetManager.
  - **Retention: handle + owner**, as with `Acquire` / `Release` on the icon. Loaded assets stay referenced until `Release(Handle)` or until the weakly referenced owner is destroyed. Releasing a load still in flight cancels it. The Blueprint nodes default the owner to self (`DefaultToSelf`); to keep assets longer, pass the game instance and release by hand. Decided over releasing at completion, which is what the engine's Async Load Asset does (`FLoadAssetActionBase` drops its handle), so anything the caller did not store is unloaded by the next GC.
  - **Blueprint nodes:** async is a `UCancellableAsyncAction` node (the node returns the action, which has `Cancel` / `IsActive`) with OnProgress / OnCompleted / OnCanceled. The node takes its data pins from the first delegate's signature only (`UK2Node_BaseAsyncTask`), so every delegate has the same one: Handle, Progress, LoadedAssets, LoadedClasses. Sync is a subsystem function.
  - **`bShowLoadingIcon`** (default false) on every request, async and sync. The loader only carries it in its events (no dependency on `LoadingFX`). The Bridge acquires the icon for flagged loads: async from start to completion or cancel, sync around the load, where MoviePlayer takes over at once and the screen turns black (the caller opts into that). An unflagged sync load only keeps an icon that is already requested animating, the same rule as LoadMap: the takeover blackens the screen the moment it starts and a blocked game thread cannot decide later, so an automatic takeover would flash black for a 5 ms load. Unflagged async loads (background preloads) never show the icon.
  - **Blocking section** on `ULoadingFXIconSubsystem` (Blueprint and C++; C++ only until 2026-11-03, when Begin / End / IsInBlockingSection became UFUNCTIONs so that Blueprint-only projects can keep the icon animating through their own sync loads): Begin / End plus an RAII scope, counted for nesting. It takes over MoviePlayer only while the icon is requested and no other loading screen is prepared or playing, and does nothing where MoviePlayer is unavailable (editor, PIE, `-NoLoadingScreen`). The Bridge, a `UGameInstanceSubsystem` depending on both modules, drives it from the loader's sync begin/end events.
- **Implemented (names approved 2026-10-12, frozen at 1.0):**
  - `ULoadingFXLoaderSubsystem`: C++ `LoadAssetsAsync(Paths, Reason, Owner, bShowLoadingIcon, OnCompleted, OnProgressChanged, OnCanceled)` and `LoadAssetsSync(Paths, Reason, Owner, bShowLoadingIcon, OutLoadedAssets)`; Blueprint `K2_LoadAssetsSync` ("Load Assets Sync"; UFUNCTIONs cannot be overloaded, hence the engine's `K2_` convention), `Release` ("Release Loaded Assets"), `ReleaseAll` ("Release All Loaded Assets"), `IsHandleActive`, `IsLoadInProgress`, `GetLoadProgress`; `FLoadingFXLoadHandle`; C++ callbacks `FLoadingFXLoadCompleted` / `FLoadingFXLoadProgressChanged` / `FLoadingFXLoadCanceled`; events `OnLoadStartedNative` / `OnLoadEndedNative` (`FLoadingFXLoadInfo`; named `Native` so a Blueprint version can take the plain name later). Console: `LoadingFX.Loader.Dump`.
  - `ULoadingFXLoadAssetsAsyncAction` ("Load Assets Async"): exec outputs On Progress / On Completed / On Canceled in that order, sharing `FLoadingFXLoadAssetsAsyncEvent`. `Cancel` releases a load in flight, so On Canceled fires from it as from any other cancel; a completed load stays with its handle. `UBlueprintAsyncActionBase::SetReadyToDestroy` does not clear `RegisteredWithGameInstance`, so `IsActive` stays true after the action finished (engine behavior).
  - Icon subsystem: `BeginBlockingSection(Reason)` / `EndBlockingSection()` / `IsInBlockingSection()` and `FLoadingFXBlockingScope(WorldContextObject, Reason)`. The section sets the loading screen up itself (the setup shared with `HandlePrepareLoadingScreen`), then calls `PlayMovie`, so PlayMovie's `OnPrepareLoadingScreen` broadcast does not ask other listeners (a project's own map loading screen) to set one up for the section. If `PlayMovie` fails, the attributes are cleared so the next map load does not inherit them. A Blueprint Begin / End pair cannot be made to match the way a scope does, so the outermost Begin binds `FCoreDelegates::OnEndFrame` (only while a section is open; broadcast once per frame, at the end of `FEngineLoop::Tick`, and nowhere else in 5.5), and a section still open there is ended with a warning: work that blocks the game thread is over by then. Left open, it would turn every later section, the Bridge's included, into a nested one that takes nothing over. MoviePlayer started inside the engine tick has already stopped by then (the engine loop calls `WaitForMovieToFinish(true)` right after `GEngine->Tick`, and with `bAutoCompleteWhenLoadingCompletes` it returns at once); started later in the frame (a core ticker), it stops in that `EndBlockingSection`.
  - The Bridge (`ULoadingFXBridgeSubsystem`) lives in `Private/` and is not API. Multicast delegates call their listeners in reverse order of binding, so a listener bound after the Bridge runs before it and may release the load first: the Bridge skips a start for a load that is no longer active, and ends only the sections it started.
  - No callback fires inside a load call. A completion that comes back inside `RequestAsyncLoad` (everything in memory with `s.StreamableDelegateDelayFrames` 0), or a request with nothing to load, completes on the next pass of the core ticker, which is the same frame when the call came from a core ticker. An asset already in memory otherwise completes a frame later (the delay defaults to 1). The engine does not fire the update delegate for the last asset, so the loader reports progress 1 right before the completion; a progress bar needs only the progress callback.
  - Only non-null paths go to the streamable manager (it logs every request that contains a null); results still follow the request, resolved with `FSoftObjectPath::ResolveObject` (which follows redirectors).
  - Checked with `LFXProto.Loader` (see Verification Prototype).
- **Engine behavior the design rests on (5.5 source, checked against 5.8):**
  - Progress is finished requested assets / requested assets (`FStreamableHandle::GetProgress`). The zen loader's `GetAsyncLoadPercentage` returns -1 (its body is commented out), so there is nothing finer. A single-asset request jumps from 0 to 1, and dependencies do not count. The update delegate fires as each requested asset finishes, so nothing polls.
  - `CancelHandle` only stops the callbacks; packages already in flight finish loading.
  - 5.6+ added `FStreamableDelegateWithHandle` and `FStreamableAsyncLoadParams`, but the 5.5 forms (`RequestAsyncLoad` with an `FStreamableDelegate`, `BindCompleteDelegate(FStreamableDelegate)`, `BindUpdateDelegate`, `GetProgress()`) still compile in 5.8, so the loader uses that common subset without version checks. BuildPlugin on 5.8 passed (2026-10-12) once the Bridge included `Subsystems/SubsystemCollection.h` for `InitializeDependency`, which 5.5 pulls in through other headers and 5.8 does not. 5.6 and 5.7 passed as well (2026-10-25).

### Findings (UE 5.5 `-game`, packaged builds on 5.5 and 5.8; engine code read for 5.5 and 5.8)

- **Material time:** Slate gives UI materials `View.RealTime = FPlatformTime::Seconds()` at draw time and `View.GameTime = FApp::CurrentTime`, which only the game thread advances (`SlateRHIRenderer.cpp`, same in 5.8). The `Time` node uses GameTime unless **Ignore Pause** is on, so spinner materials must enable Ignore Pause. Confirmed visually (5.5 `-game`, 30 s block): the RealTime spinners animate under MoviePlayer and the GameTime variant freezes.
- **Manual MoviePlayer around a sync load works:** `SetupLoadingScreen` → `PlayMovie()` → blocking work → `WaitForMovieToFinish()`. The widget was painted about 60 times per second, all off the game thread. The engine loop also calls `WaitForMovieToFinish(true)` right after `GEngine->Tick()` every frame, which restores the game viewport afterwards.
- **LoadMap:** MoviePlayer hooks `PreLoadMap` itself and calls `PlayMovie()`, which broadcasts `OnPrepareLoadingScreen` when nothing is set up. Binding that event (not `PreLoadMap`, whose call order is not guaranteed) gives the v1 behavior: take over only when the icon is visible. Loading screen attributes are cleared after every playback.
- **Background:** the MoviePlayer root is `SDefaultMovieBorder` with `BlackBrush`, so the screen behind a loading screen widget is black while blocked (same in 5.8). The last game frame is not shown. The widget itself goes into a full-screen slot over it (`SOverlay` slot → `SDPIScaler` → `SBorder` with `NoBorder` and no padding, `DefaultGameMoviePlayer.cpp`), which is how the plugin's background color covers the black.
- **GC:** materials held by a `UPROPERTY` survived a `CollectGarbage` run in the middle of the blocked section, and LoadMap's own GC.
- **Packaged builds:** `LFXProto.RunAll` gives the same results in packaged Development builds on 5.5 and 5.8 (the 5.8 build was made from a copy of the project, so this project's content was never saved with 5.8). Plugin assets loaded only by path are not cooked on their own; this project lists `/LoadingFX` in `DirectoriesToAlwaysCook` (`DefaultGame.ini`).
- **Icon material preload (2026-10-11, 5.5):** in a packaged Development build (D3D12) the preload was ready 5.9 ms after the request, before the startup LoadMap. At the first `Acquire` all 10 Slate graphics PSOs of `M_LoadingDotRing` were compiled, and `Acquire` took 0.03 ms with no sync load. `M_LoadingArc`, loaded on demand at the same moment, had none of its PSOs collected yet right after the load (the collection runs asynchronously after PostLoad); its 10 were compiled 3 s later. With `-LFXProtoEarlyAcquire` the wait for the in-flight preload took 0.1 ms packaged and 4.6 ms in `-game`, and the icon then took over the startup LoadMap through MoviePlayer. In `-game` (uncooked) the completion delegate only runs at the first async-loading tick, which during engine init is the startup LoadMap, so the log shows it 0.7 to 1 s after the request although the load itself takes a few ms. A missing material path logs one warning and draws nothing (also with an early `Acquire`); a material already in memory (tested with the non-UI `WorldGridMaterial`, which also warns) is taken without a load.
- **On-demand shaders in uncooked runs (issue #5, 2026-10-29, 5.5 `-game` and packaged; reported on 5.8 `-game`):** with the shader job cache enabled (the default), `IsMaterialMapDDCEnabled()` is false outside the cooker (`ShaderCompilerJobCache.cpp`, same in 5.8), so `UMaterial::PostLoad` caches with `EMaterialShaderPrecompileMode::None`: a loaded material has no shaders yet, and `FMaterial::TryGetShaders` starts compiling them (ForceLocal) when it is first drawn. Only the game thread takes the results in (`GShaderCompilingManager->ProcessAsyncResults`). When that first draw was on MoviePlayer's loading thread, Slate found no shaders and skipped the batch (`SlateRHIRenderingPolicy.cpp`, `TryGetShaders` fails for the material and its fallback), so the loading screen stayed black until LoadMap's own `ProcessAsyncResults` near its end. `LFXProto.IconTravel ... cold` before the fix: the icon on 1 of 218 loading screen frames after the show delay, and that one 3.66 s late, right after LoadMap processed the results. After the fix (`UMaterialInterface::EnsureIsComplete` when the material arrives, see the preload bullet): 216 of 216, the first 4 ms after the deadline; the compile took 1471 ms on the first run (the shaders not in the job cache yet) and 23 to 43 ms afterwards. A packaged Development build drew 212 of 212 frames with no compile, so cooked builds were never affected. This also explains the issue's note that the first run after adding the plugin showed no icon at all.

### Cooking the default material (UE 5.5 `-run=Cook`; engine source read for 5.5)

Verified 2026-10-08 with a throwaway probe (a `UDeveloperSettings` class holding two `TSoftObjectPtr<UMaterialInterface>` properties, plus a `FGameDelegates::GetModifyCookDelegate()` handler in the game module) while `/LoadingFX` was removed from `DirectoriesToAlwaysCook`. The probe was reverted; the log is `Saved/Logs/CookProbe_Cook.log` (local only). Instigators are printed with `-dpcvars=cook.displaymode=6`.

- **Soft references read from an ini are cooked automatically.** `FSoftObjectPath::ImportTextItem` reports the value to `GRedirectCollector` ("Consider this a load, so Config string references get cooked"), and `StartCookByTheBook` requests those packages with instigator `StartupSoftObjectPath`. Confirmed: `M_LoadingDotGrid`, referenced only by a `DefaultGame.ini` line, was cooked. So a material the user picks in Project Settings is cooked with no extra setup.
- **A C++ constructor default is not cooked.** Only ini text is collected; the CDO holding `M_LoadingDotRing` as its constructor default did not get it cooked (negative control). This is exactly the untouched-default case.
- **`FGameDelegates::Get().GetModifyCookDelegate()` is the official plugin hook.** Multicast, listed by `-helpcookusage` ("Subscribe to this delegate during your module startup"), called from `UCookOnTheFlyServer::CollectFilesToCook` right after `UAssetManager::ModifyCook`. Confirmed: `M_LoadingBoxes` added by the handler was cooked with instigator `ModifyCookDelegate`; its material functions followed as `HardDependency`.
- **Implemented:** `ULoadingFXSettings::LoadingIconMaterial` (`Config=Game`, `DefaultConfig`, constructor default `M_LoadingDotRing`; Project Settings > Plugins > LoadingFX) and `FLoadingFXModule::OnModifyCook`, bound to `GetModifyCookDelegate()` in `StartupModule` under `WITH_EDITOR` and removed in `ShutdownModule`. It adds the package of the effective material (default or user override) to `PackagesToCook`, so user projects need no `DirectoriesToAlwaysCook` entry.
- **Alternatives considered.** A plugin-shipped `Config/Game.ini` with `+DirectoriesToAlwaysCook=(Path="/LoadingFX")` works and has Epic precedent (`Engine/Plugins/NNE/NNEDenoiser/Config/Game.ini`), but cooks every bundled spinner. Plugin ini files are dynamic config layers applied *after* the project's `Default*.ini` (`FConfigBranch::AddDynamicLayersToHierarchy`), so never put a scalar default such as the material path in one: it would override the user's choice. `UPrimaryAssetLabel` needs project-side `PrimaryAssetTypesToScan` edits (the default type is `bIsEditorOnly=True`, `CookRule=Unknown`, scans `/Game` only, and only one entry per type is allowed). Loading the material at startup (hard reference in a native CDO) is cooked as `StartupPackage` but forces an eager load in every process. `GetCookModificationDelegate` is deprecated since 5.0.
- `SkipOnlyEditorOnly=true` is the 5.5 default (`BaseEditor.ini`), so packages merely loaded during the cook are not cooked unless a cooked package references them.
- This project keeps `+DirectoriesToAlwaysCook=(Path="/LoadingFX")` because the prototype loads every spinner by path at runtime.

## Conventions

- Copyright header: `// Copyright (c) 2026 Kurorekishi (EmbarrassingMoment).`
- `PCHUsage = UseExplicitOrSharedPCHs`; always include the module's own header explicitly.
- Use `Category = "LoadingFX"` for `UFUNCTION` / `UPROPERTY`.

- `Plugins/LoadingFX/AGENTS.md` is the usage guide for AI agents in users' projects (shipped with the plugin, listed in `FilterPlugin.ini`; `Plugins/LoadingFX/CLAUDE.md` tells Claude Code to read it in a sentence, then imports it: Claude Code loads a nested `CLAUDE.md` only once it reads a file in that folder, and there it passed the `@AGENTS.md` line on as text instead of expanding it (seen on 2026-11-02 and 2026-11-03, issue #16), so the sentence is what reaches the agent). It is not about developing the plugin. Its *Verifying it* section must work without tools the user may not have: the log comes first, and a recording only after checking that a recorder is installed, never installing one unasked. Update it with any change to the public API, the settings, the bundled materials or their parameters, and the known pitfalls.
